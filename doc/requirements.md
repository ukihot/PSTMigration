# PSTメールアーカイブ自動収集ツール 要件定義書

- 文書版数：1.0
- システム名：PSTMigration
- 開発言語：Python
- 配布形式：Windows実行ファイル（EXE）
- 配布方式：Active Directory グループポリシー（GPO）

---

# 1. 背景・目的

## 1.1 背景

当社では、従来TOKAI OneOfficeのPOPメールをClassic Outlookで利用していた。

2026年4月頃から各従業員が順次IMAP方式へ移行しており、現在はPOPアカウントを削除済みである。

ただし、POP運用時代のメールはOutlookデータファイル（PST）として各PCに残存しており、現在もOutlookにデータファイルとして接続されている。

今後、Microsoft 365 Business Standardを約100アカウント導入し、以下の移行を計画している。

- OneOffice IMAP → Exchange Online
- オンプレミスAD → Microsoft Entra ID
- ファイルサーバ → SharePoint Online
- 既存オンプレミスサーバの廃止

OneOffice上のメールはベンダーがExchange Onlineへ移行するが、過去のPOPメールについては移行対象外である。

また、OneOfficeのサーバ容量は1,500,000MBであり、既に約1,123,750MBを使用しているため、過去のPOPメールをOneOfficeにアップロードする運用は採用できない。

## 1.2 目的

各PCに残存するPOP時代のPSTを自動的に収集し、Microsoft 365への移行準備を行う。

具体的には、以下を実現する。

1. PSTの自動検出
2. メールの日付によるPST分割
3. 2020年以前のメールの7z圧縮
4. ファイルサーバへの自動転送
5. 処理結果の記録と集約
6. 処理失敗時の安全な再実行
7. 元PSTの完全性保護

従業員による手作業を不要とし、情報システム担当者による集中管理を実現する。

# 2. システム概要

## 2.1 基本方針

| 項目 | 方針 |
|---|---|
| 開発言語 | Python 3 |
| Outlook操作 | pywin32（COM） |
| 圧縮処理 | 7-Zip CLI |
| EXE化 | PyInstaller |
| 実行環境 | Windows 10 / Windows 11 |
| Outlook | Classic Outlook 2016 / 2019 / 2024 / Microsoft 365 |

| 実行方式 | 無人・非対話操作 |

| 処理単位 | PSTファイル単位 |
| ログ形式 | JSON |
| 日付分割基準 | 2021年1月1日 00:00:00 |

Python実行環境を各PCにインストールする必要はない。

EXEはGPOから起動する。

## 2.2 処理フロー

1. ユーザーログオン
2. GPOのスケジュールタスク起動
3. 実行済み状態の確認
4. Outlook環境の確認
5. PSTファイルの自動検出
6. 対象PSTの事前調査
7. PST分割処理
8. 分割結果の検証
9. 2020年以前PSTの7z圧縮
10. 圧縮ファイルの整合性検証
11. ファイルサーバへ転送
12. 転送結果の検証
13. 完了ログの出力
14. 処理終了

処理中にエラーが発生した場合は、エラーを記録して安全に終了する。

# 3. 機能要件

## FR-01 PST自動検出

### 概要

現在ログオンしているユーザーのOutlook環境からPSTを自動検出する。

### 要件

- Outlook MAPIのStoresコレクションを使用する。
- FilePathを持つPSTストアを抽出する。
- IMAPアカウントのOSTファイルは対象外とする。
- 複数PSTが存在する場合はすべて処理する。
- 同一PSTの重複検出を防止する。
- ファイル名や保存場所に依存しない。
- Outlookに登録されていないPSTは原則として対象外とする。
- 既に生成済みの分割PSTは対象外とする。

### 対象例

- Outlookデータファイル
- 個人用フォルダー
- 過去メール
- 旧POPアカウントのPST

PSTの表示名ではなく、ファイル形式と実体パスを基準に判定する。

## FR-02 日付分割

### 概要

PST内のメールを2021年1月1日を境に分割する。

### 分割条件

| メール日時 | 出力先 |
|---|---|
| 2020/12/31 23:59:59以前 | 旧メールPST |
| 2021/01/01 00:00:00以降 | 新メールPST |

### 日付判定

受信メール：
- ReceivedTimeを優先する。
- 取得不能な場合はSentOnを使用する。

送信メール：
- SentOnを優先する。
- 取得不能な場合はReceivedTimeを使用する。

日付取得不能なメールは削除せず、エラーとして記録する。

### フォルダー構造

以下の構造を原則として維持する。

- 受信トレイ
- 送信済みアイテム
- 削除済みアイテム
- ユーザー作成フォルダー
- 多階層サブフォルダー

検索フォルダーは対象外とする。

メール以外のアイテムは検出・記録し、黙って破棄しない。

予定表、連絡先、タスク等の移行要否については別途決定する。

## FR-03 元PSTの保護

### 概要

既存PSTを変更・削除・破損させない。

### 必須要件

- 元PSTに対するメール削除は禁止する。
- 元PSTのMove操作は禁止する。
- 分割処理に伴う元PSTの恒久的な変更を禁止する。
- 元PSTを上書きしない。
- 処理中断時にも元PSTを保持する。
- 原本を変更する可能性がある処理は作業用コピー上で行う。

### Outlook COM利用時の注意

MailItem.Copy()はコピー元フォルダーに一時アイテムを作成する場合がある。

そのため、業務用PSTに直接Copy()を繰り返す実装は禁止する。

読み取り専用のPST解析方式、または検証済みの作業用コピー方式を採用する。

OutlookでPSTが接続中の場合、ファイル単純コピーによる整合性は保証されない。

安全なスナップショット取得方法を設計・検証すること。

## FR-04 旧メールPSTの圧縮

### 概要

2020年以前のPSTを7z形式で圧縮する。

### 要件

- 7-ZipのCLIを利用する。
- 原則としてLZMA2を使用する。
- 初期圧縮レベルは5とする。
- 元PSTを圧縮処理中に変更しない。
- 圧縮完了後に7zのテストコマンドを実行する。
- 圧縮失敗時は元データを保持する。
- 圧縮成功だけをもって移行成功とは判断しない。

### 出力例

old_mail_before_20210101.7z

圧縮率はPST内の添付ファイルなどに依存する。

一定の圧縮率を必須要件とはしない。

## FR-05 新メールPSTの生成

### 概要

2021年以降のメールをExchange Online移行用PSTとして生成する。

### 要件

- PST形式を維持する。
- 圧縮しない。
- Unicode PST形式とする。
- Microsoft Purviewによるインポートを想定する。
- フォルダー階層を保持する。
- メール本文と添付ファイルを保持する。
- 送信者、宛先、送受信日時などの主要属性を保持する。
- ファイルサイズを記録する。
- 大容量PSTは必要に応じて追加分割する。

Microsoft Purviewへの投入を考慮し、原則として1ファイル20GB以下を推奨する。

20GBを超える場合の自動再分割は追加設計事項とする。

## FR-06 ファイルサーバへの自動転送

### 概要

生成されたファイルを社内ファイルサーバへ転送する。

### 保存先構造

\\FILESERVER\PST-Migration\
    user001\
        old_mail_before_20210101.7z
        new_mail_from_20210101.pst
        report.json
    user002\
        old_mail_before_20210101.7z
        new_mail_from_20210101.pst
        report.json

実際のサーバ名、共有名は設定ファイルで指定する。

### 要件

- Windowsログオンユーザーの認証情報を使用する。
- 追加のID・パスワード入力を要求しない。
- ユーザーごとに保存先を分離する。
- 複数PSTを処理した場合もファイルが衝突しない命名規則を採用する。
- 転送中は一時ファイル名を使用する。
- 転送完了後に正式ファイル名へ変更する。
- SHA-256による整合性確認を実施する。
- 転送失敗時は次回実行で再試行する。
- 既存の正常な収集ファイルは上書きしない。

### アクセス制御

- 情報システム管理者：全フォルダーの参照・管理
- 一般ユーザー：自分の収集先への必要最小限の書き込み
- 他ユーザーのPST：参照不可

原則として一般ユーザーに他社員のメールデータを参照させない。

## FR-07 ログ・処理結果管理

### 概要

各PCの処理状況を情報システム側で把握できるようにする。

### 記録項目

- 実行日時
- コンピューター名
- Windowsユーザー名
- ツールバージョン
- 元PSTパス
- 元PSTサイズ
- 処理対象メール件数
- 2020年以前のメール件数
- 2021年以降のメール件数
- コピー成功件数
- スキップ件数
- エラー件数
- 圧縮前容量
- 圧縮後容量
- 圧縮率
- 転送先
- SHA-256
- 処理時間
- 最終ステータス
- エラー詳細

### ステータス定義

| ステータス | 意味 |
|---|---|
| PENDING | 未処理 |
| SCANNING | PST調査中 |
| SPLITTING | 分割中 |
| COMPRESSING | 圧縮中 |
| TRANSFERRING | 転送中 |
| VERIFYING | 検証中 |
| COMPLETED | 正常完了 |
| FAILED | 処理失敗 |
| RETRY_PENDING | 再試行待ち |
| SKIPPED | 対象外 |

### ログ出力

- ローカル：JSON
- ファイルサーバ：JSON
- 集計用：CSV

ログには原則としてメール本文を記録しない。

件名・送信者などの個人情報も、障害解析に必要な最小限に限定する。

## FR-08 再実行制御

### 概要

ログオンするたびに同じPSTを再処理しない。

### 要件

- PST単位で完了状態を記録する。
- 完了済みPSTは再処理しない。
- 実行中の多重起動を禁止する。
- 処理失敗時は再試行可能とする。
- 転送失敗だけの場合、原則として分割・圧縮をやり直さない。
- 出力ファイルが欠落している場合は完了扱いにしない。
- 元PSTが更新された場合は変更を検出する。

### PST識別情報

- ファイルパス
- ファイルサイズ
- 最終更新日時
- 必要に応じてハッシュ値

単純なファイル名だけで完了判定しない。

## FR-09 GPO配布・自動実行

### 概要

Active DirectoryのGPOで全社PCへツールを配布する。

### GPO設定

| 項目 | 設定 |
|---|---|
| 配布対象 | 対象ユーザーまたはPC |
| 配布方式 | グループポリシー基本設定 |
| 実行方法 | タスクスケジューラ |
| トリガー | ユーザーログオン時 |
| 実行タイミング | ログオン後、遅延実行 |
| 実行アカウント | ログオンユーザー |
| 実行条件 | ユーザーがログオンしているときのみ |
| 多重起動 | 禁止 |
| 管理者権限 | 原則不要 |
| ネットワーク | 社内ファイルサーバへの接続が必要 |

### 運用要件

- 従業員にコマンド入力を要求しない。
- 従業員にPython環境をインストールさせない。
- 通常業務を妨げない。
- 不必要な画面や進捗ダイアログを表示しない。
- エラー時に無限ループしない。
- 実行状況は管理者が確認できる。
- 実行内容は社内の情報管理規程に沿って周知する。

業務端末への負荷を抑えるため、処理の同時実行台数を制御できることが望ましい。

## FR-10 一時領域管理

### 概要

分割・圧縮に使用する作業領域を管理する。

### 要件

- 処理開始前にディスク空き容量を確認する。
- 空き容量不足なら処理を開始しない。
- 一時ファイルは専用作業フォルダーに生成する。
- 処理失敗時に原本を削除しない。
- 転送完了後、検証済みの一時ファイルのみ整理する。
- 処理中断時の一時ファイルは再試行時に判別できるようにする。

必要な空き容量は元PSTのサイズと分割方法から算出する。

固定の空き容量だけで判定しない。

# 4. 非機能要件

## 4.1 性能

- 通常のOutlook操作に著しい影響を与えない。
- CPU・ディスクI/Oの負荷を抑える。
- 大容量PSTを処理できる。
- 処理時間が長くてもタイムアウトで無条件終了しない。
- 処理中のシャットダウンや通信断を想定する。
- ネットワーク転送を制御し、VPN回線への過度な負荷を避ける。

## 4.2 可用性

- 一時的な障害から再試行できる。
- 元データを保全する。
- 途中失敗したファイルを正常完了と誤認しない。
- 部分的な成功・失敗をPST単位で記録する。
- 同一PC上で同時に複数の処理インスタンスを起動しない。

## 4.3 セキュリティ

- 元PSTを削除しない。
- 不要な管理者権限を要求しない。
- PSTを外部サービスへ送信しない。
- 転送先は社内指定ファイルサーバに限定する。
- 共有フォルダーはNTFS権限と共有権限で保護する。
- ツール改ざんを防ぐため、配布ファイルのハッシュを管理する。
- EXEのデジタル署名は導入条件・費用を踏まえて検討する。
- ESET Endpoint Antivirusとの互換性を事前検証する。
- 通常のセキュリティ監視機能を無効化しない。

## 4.4 保守性

- 設定値はコードから分離する。
- 日付基準を変更可能にする。
- 転送先を変更可能にする。
- ツールバージョンをログに記録する。
- エラー発生箇所を特定可能にする。
- Pythonソースコードを保守用に保持する。
- EXEを更新しても既存の正常な処理結果を再利用できる。

# 5. データ保存方針

## 5.1 2020年以前のメール

保存形式：
- 7z圧縮されたPST

一次保存先：
- 旧ファイルサーバ

最終保存先：
- SharePoint Online

用途：
- 長期アーカイブ
- 必要時のみ展開・閲覧

SharePoint上のPSTをOutlookから直接使用しない。

必要な場合はローカルへダウンロードして展開する。

## 5.2 2021年以降のメール

保存形式：
- PST（無圧縮）

一次保存先：
- 旧ファイルサーバ

移行先：
- Exchange Online

移行方法：
- Microsoft PurviewのPSTインポート機能
- AzCopyによるアップロード

OneOfficeのIMAPサーバは経由しない。

## 5.3 重複メール対策

OneOfficeのIMAPメールはベンダーがExchange Onlineへ移行する。

一部のメールは、POP時代のPSTとIMAPサーバの両方に存在する可能性がある。

そのため、PSTインポート時は重複メールを考慮する。

要件：

- PST分割時に2026年4月以降を一律に除外しない。
- POP→IMAP切替日はユーザーごとに異なるものとして扱う。
- Exchange上の既存メールとの重複を検証する。
- Message-ID等を利用した照合方式を検討する。
- 同一Message-IDだけでは完全な重複判定にならない点を考慮する。
- 重複防止のためにメール欠落を発生させない。
- 本番インポート前に試験ユーザーで検証する。

Microsoft Purviewの標準インポートだけで、IMAP移行済みメールとの完全な重複排除が保証されるものとはしない。

実施内容：

# 7. テスト要件

## 7.1 機能テスト

- 単一PSTの検出
- 複数PSTの検出
- IMAPストアの除外
- 空フォルダーの処理
- 多階層フォルダーの処理
- 送信メールの日付判定
- 受信メールの日付判定
- 日付取得不能メールの処理
- 2020年12月31日と2021年1月1日の境界判定
- 同名PSTの衝突防止
- 7z圧縮・展開
- 転送後ハッシュ一致
- 完了済みPSTの再処理防止

## 7.2 障害テスト

- Outlook起動中
- Outlook終了中
- PSTアクセス失敗
- PST破損
- ディスク空き容量不足
- ネットワーク切断
- ファイルサーバ停止
- 転送途中の強制終了
- Windowsログオフ
- PCシャットダウン
- 処理中の再ログオン
- 同時起動
- 圧縮失敗
- 転送先権限不足

## 7.3 データ整合性テスト

以下を検証する。

- 元PSTの主要メール件数
- 旧メールPSTの件数
- 新メールPSTの件数
- 日付取得不能件数
- コピー失敗件数
- 元PSTの完全性
- フォルダー階層
- 添付ファイル
- 送受信日時
- 主要メール属性

原則として以下が成立すること。

元PSTの対象メール件数
=
旧メールPSTの件数
+
新メールPSTの件数
+
未移行メール件数

未移行メール件数が0件であることを正常完了の条件とする。

メール以外のアイテムは別途集計・判定する。

# 8. 受入基準

以下をすべて満たした場合に受入完了とする。

1. 従業員の手作業なしで実行できる。
2. GPOによる配布・起動が正常に動作する。
3. Outlook上の対象PSTを検出できる。
4. 2021年1月1日を基準に正しく分割できる。
5. 元PSTが意図せず変更・削除されない。
6. フォルダー構造とメール属性が保持される。
7. 2020年以前のPSTを7z圧縮できる。
